## 重要问题（建议实现前决策）

- [x] CHK001 - 是否要求「`grade` 残留」直接导致构建失败，而不只是约定「代码里不再使用」？ [Completeness, Spec §FR-009/§FR-011; Gap]
  - **评审结论（2026-11-22）**：不需要；不新增构建期门禁，已从 plan / data-model / contracts / quickstart 移除。
  - **解释**：现有 schema 使用 `z.object`，JSON 里多写的 `grade` 会被 Zod 静默丢弃，构建仍可能通过。这样「彻底删除年级字段」只靠人工 grep 保证，维护者以后重新加回 `grade` 也不会被拦住。评审前 plan 与 contracts 曾写了「残留即失败」，现已按评审决定移除；spec 的 FR-009 只列了 `directions` 的失败场景。
  - **建议**：在 FR-009 增加「记录残留 `grade` 时构建失败」，或新增一条 FR；错误信息包含 `src/data/students.json`、学生姓名与 `grade`。实现时需读取原始 JSON 做键检查（Zod 对象级 refine 看不到被丢弃的未知键）。

- [x] CHK002 - 成员链接来源的分类边界是否足以让 31 条记录的判定结果一致？ [Clarity, Spec §FR-015/§FR-016; Ambiguity]
  - **评审结论（2026-11-22）**：不需要补充平台清单；沿用四档优先级与强关联证据逐条判断。
  - **解释**：规格只给了「自建个人主页 → 机构个人资料页 → GitHub → Scholar」的优先级与几个例子，没有说明 LinkedIn、ORCID、ResearchGate、个人博客、研究所成员列表页、Google Sites 等算哪一类，也没说明「机构资料页」是否仍显示 `Homepage` 标签。不同人按不同理解填写，31 条数据会出现不一致，返工成本高。
  - **建议**：在 `contracts/students-data.md §2.3` 增加「计入 / 不计入」清单与兜底规则：例如自建域名、GitHub Pages 学术主页、Google Sites 计入 `url`；机构个人页计入 `url`；LinkedIn / ORCID / ResearchGate / 搜索引擎结果不计入；只有这些来源时保持 `null`。同时明确机构资料页沿用 `Homepage` 标签（若改为 `Profile`，需同步修改 FR-019）。

- [x] CHK003 - 每条非空链接与每个「无链接」结论是否必须留下可复核的证据记录？ [Completeness, Spec §FR-016/§SC-006/§SC-007; Gap]
  - **评审结论（2026-11-22）**：不需要；不新增证据文件或对应 FR/SC，无链接学生只在完成报告中列出。
  - **解释**：FR-016 要求「写入前取得强关联证据」，但没有要求把证据写下来；SC-006 只说链接「可公开核实」，SC-007 只要求列出无链接学生。评审前 contracts 曾要求 `evidence/student-links.md`，现已按评审决定移除；spec 的成功标准仍没有对应的验收项。
  - **建议**：新增 FR：「每个非空链接 MUST 在证据文件中记录 URL、证据类型（机构页 / 导师页 / 合作论文等）、证据摘要或引用、核实日期与最终决策」；新增 SC：「100% 非空链接有对应证据记录；无链接学生有候选来源与被排除原因」。这样 SC-006/SC-007 才可审计。

- [x] CHK004 - SC-001「全页无入学年份」与 FR-013「Graduates 的 `year` 保留」的验收口径是否冲突？ [Conflict, Spec §SC-001 vs §FR-013; Measurability]
  - **评审结论（2026-11-22）**：已改为「两个在读分组内不出现入学年份」；全页只查 "Since" 为 0。
  - **解释**：Team 页的 Graduates 区块会显示毕业年份（当前 3 条有 `year`），它们是四位数字，但不是入学年份。若按 SC-001 字面做「全页四位年份 0 处」，会把合法的毕业年份误判为失败；contracts/team-row.md §6 已把检查范围收窄到「在读分组内」，但 spec 仍写「全页」。
  - **建议**：把 SC-001 改为两句：「全页不出现 `Since`；两个在读分组内不出现四位入学年份（正则检查限定在这两个分组）」。并在验收说明中明确 Graduates 的 `year` 不计入。

## 次重要问题（建议确认）

- [x] CHK005 - `directions` 的前后空白与重复项是否有明确处理规则？ [Consistency, Spec §FR-009; Gap]
  - **评审结论（2026-11-22）**：原样渲染；前后空格与重复项由维护者避免，不新增校验。
  - **解释**：校验只拒绝空字符串和纯空白字符串，所以 `" NLP "` 会通过；渲染又规定「原样显示、不 trim」，于是标签两侧会带不可见空格。重复项（如 `["NLP", "NLP"]`）也会原样显示两次。规格没有说这是允许的还是应拒绝。
  - **建议**：二选一并写进契约：(a) 构建期拒绝 `item !== item.trim()` 的项，重复项允许但 README 说明会显示两次；(b) 明确「原样渲染，前后空格与重复项由维护者自行避免」。推荐 (a)，数据更干净，且不影响「渲染不 trim」的承诺。

- [x] CHK006 - 「可辨识的标签样式」与「一组方向信息的语义」是否已量化到可验收？ [Measurability, Spec §FR-005/§FR-014]
  - **评审结论（2026-11-22）**：接受建议；FR-005 引用教师 chip 视觉，FR-014 写明 `role="list"` + `aria-label`。
  - **解释**：FR-005 只说标签要和姓名、链接「视觉上可区分」，FR-014 只说「以一组方向信息的语义呈现」。具体的 chip 颜色、字号、圆角，以及 `role="list"` / `aria-label="Research directions"` 只写在 plan 与 contracts 里。评审者只看 spec 时无法判断「可辨识」到什么程度，也无法判断语义是否达标。
  - **建议**：在 FR-005 补一句「视觉基线以 `contracts/team-row.md §5` 为准（`--sky` 背景、4px 圆角、0.9rem、`--ink-soft`）」，在 FR-014 补「`role="list"` + `aria-label="Research directions"`，子项 `role="listitem"`」。这样 spec 与契约有单一可追踪的验收口径。

- [x] CHK007 - 成功标准中的「31 条」是否应绑定数据快照，而不是写死数字？ [Measurability, Spec §SC-001/§SC-004]
  - **评审结论（2026-11-22）**：不绑定快照；沿用当前 31 条基线，不引入快照机制。
  - **解释**：当前数据是 31 条（PhD 20 / Master's 11），但实现期间可能新增或移除学生。SC-001 写死 31，一旦名单变动，验收就会失败；规格没有说明「以哪一天的数据为准」。
  - **建议**：在 Assumptions 或 SC 里写明「基线 = 2026-11-22 的 `students.json` 快照，共 31 条」；验收按「基线内 100% 记录」判定。若名单在实现期间变化，先更新基线再验收，而不是把新名单算作失败。

- [x] CHK008 - 无链接行是否必须保留链接列宽度，以保证标签组可用宽度一致？ [Clarity, Spec §FR-017; Gap]
  - **评审结论（2026-11-22）**：固定三轨天然保留链接列宽，无需额外占位；已写入 FR-017 与行布局契约。
  - **解释**：contracts/team-row.md §3 要求「无链接行保留 117px 链接列宽」，这样有链接和无链接行的标签组宽度一致；但 spec 的 FR-017 只说「不渲染空洞的链接标签」，没有说列宽是否保留。实现者若让标签组扩张到空列，行与行之间的换行位置会不同，视觉上不整齐。
  - **建议**：在 FR-017 补「≥480px 时无链接行 MUST 保留链接列宽，标签组可用宽度与有链接行一致」；如果决定允许扩张，也要明确写出，避免实现与验收各按一套理解。
