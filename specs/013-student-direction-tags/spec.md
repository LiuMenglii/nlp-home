# Feature Specification: Team 页在读学生的研究方向标签（替换年级字段）

**Feature Branch**: `013-student-direction-tags`

**Created**: 2026-11-22

**Status**: Draft

**Input**: User description: "请将 team 界面在读学生的年级修改为研究方向的标签。彻底删除年级的字段。现在的研究方向全部写成占位符。"

## 目标与范围

Team 页的两个在读学生分组（PhD Candidates、Master's Students）当前每行显示「姓名 → Since 入学年份 → 成员链接」，其中入学年份来自学生数据的 `grade` 字段，名单也按 `grade` 升序排列。

本特性把「年级」整体替换为「研究方向标签」：

1. **数据字段替换**：学生数据以 `directions`（研究方向标签，字符串数组，至少 1 项）取代 `grade`；`grade` 字段从数据文件、数据校验规则、页面渲染与数据维护文档中彻底删除，不再有任何来源或展示入学年份。
2. **页面展示替换**：在读学生每行不再显示 "Since YYYY"，改为显示该学生的全部研究方向标签；标签以可识别的标签样式呈现，与姓名、成员链接在同一行内区分明确。
3. **占位内容**：当前全部在读学生的 `directions` 一律写为占位符 `["TBD"]`，页面按原文显示 `TBD`；不得留空、不得省略该字段。
4. **排序规则调整**：名单不再按年级排序，每个分组内按数据文件条目顺序展示（既有的按 level 分组、≥768px 两栏切分与栏内顺序规则不变）。
5. **既有约束保留**：姓名居左、成员链接居右、每行左右 24px 内距、双栏结构与 32px 栏距、分组标题、每人至多一个链接（`url` / `github` / `scholar` 三选一）、空分组占位文案均延续既有行为。
6. **主页链接补全（2026-11-22 补充）**：为全部在读学生补全成员链接，按「自建个人主页（含 GitHub Pages 学术主页）→ 机构个人资料页 → GitHub → Google Scholar」的优先级择一填写；无法核实归属的链接不写入，三个链接字段保持为空。

**范围之外**：

- Graduates 名单及其 `year`（毕业年份）字段——毕业年份不是年级字段，保持现状；
- 毕业生（`graduates.json`）与教师（`teachers.json`）的链接补全或重新核实；
- Faculty 卡片的研究方向样式与数据、首页、发表页、新闻页、导航与页脚；
- 新增筛选、排序控件、折叠、分页、动效或交互；
- 历史变更记录（`specs/001`–`012` 下的已有文档）——作为过去决策的归档，不回溯改写；
- 为真实研究方向新增数据源或自动抓取；本期只提供占位符与可替换的数据结构。

## Clarifications

### Session 2026-11-22

- Q: 每位在读学生的研究方向显示为几个标签？ → A: 多个标签；数据为 `directions` 数组（与教师研究方向的数据形态一致），行内展示该学生的全部标签。
- Q: 研究方向占位符使用什么文案？ → A: `TBD`。
- Q: 当一名学生同时能找到个人主页、GitHub 和 Google Scholar 时，成员行应只显示一个链接，还是并列显示多个链接？ → A: 只显示一个；按优先级保留最高的一个，并用更高优先级来源替换现有低优先级链接。
- Q: 判定一个网页属于本组在读学生时，需要多强的证据才允许写入数据？ → A: 需至少一项强关联证据（页面或公开资料明确关联中科院信工所/国科大/G3（CIGMA）/在读层次/导师，或有与课题组成员合作的论文）；仅同名不写入。
- Q: 如果某位学生找不到任何可核实的主页、GitHub 或 Google Scholar，数据中应如何处理？ → A: 三个链接字段保持 `null`，页面不显示链接，并在完成报告中列出该学生。
- Q: 「个人主页」的范围如何界定，国科大或研究所的个人资料页算不算？ → A: 自建个人站（含 GitHub Pages 学术主页）优先，其次机构个人资料页，再次 GitHub，最后 Google Scholar。
- Q: 是否要求 `grade` 残留直接导致构建失败？ → A: 不需要；不新增防御性校验，只要求数据文件、schema、组件与文档中不保留 `grade`。
- Q: 是否补充成员链接平台分类清单（LinkedIn / ORCID / ResearchGate 等）？ → A: 不需要；沿用现有四档优先级与强关联证据逐条判断。
- Q: 是否要求单独记录链接核实证据文件？ → A: 不需要；不新增证据文件或对应 FR/SC，无链接学生仍在完成报告中列出。
- Q: 「全页无入学年份」的验收范围是什么？ → A: 改为两个在读学生分组内不出现入学年份；全页只检查 "Since" 为 0，Graduates 的 `year`（毕业年份）不受影响。
- Q: `directions` 含前后空格或重复项时如何处理？ → A: 原样渲染，不 trim、不去重；由维护者避免前后空格与重复项，不新增校验。
- Q: 标签视觉与无障碍语义是否需要写入 spec？ → A: 是；FR-005 引用教师 chip 既有视觉，FR-014 写明 `role="list"` + `aria-label="Research directions"`。
- Q: 成功标准的 31 条是否绑定数据快照？ → A: 不绑定；沿用当前 31 条基线，不引入快照机制。
- Q: 无链接行是否需要额外保留链接列宽？ → A: 不需要额外占位元素；≥480px 固定三轨（3.5em / 1fr / 6.5em）天然保留第三轨，标签组可用宽度与有链接行一致。
- Q: 姓名列是否要为 4 字姓名调整？ → A: 保持 3.5em；4 字姓名在列内换行，当前名单最多 3 个汉字。
- Q: 其他页面的回归验收如何表述？ → A: 删除截图对比类验收；以相关源文件与数据文件零 diff（`git diff`）加构建通过为准，严格不改动本特性 4 个源文件之外的代码。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 访客看到研究方向标签而非年级 (Priority: P1)

访客在 Team 页浏览 PhD Candidates 或 Master's Students 分组时，每条记录显示姓名、若干研究方向标签与（可选的）成员链接。两个在读学生分组内不再出现 "Since" 或入学年份；当前每条记录显示一个 `TBD` 占位标签，访客能看出这是一个待补充的方向标记，而不是缺失数据。

**Why this priority**: 这是用户本次直接要求的展示变更；只完成数据与展示替换即可独立交付价值。

**Independent Test**: 打开 Team 页（或构建产物），确认两个在读分组中 31 条记录均显示至少一个方向标签，且两个在读分组内无 "Since" 与四位年份形式的入学年份；全页范围另确认 "Since" 为 0。用检索确认页面源码中不再引用 `grade`。

**Acceptance Scenarios**:

1. **Given** 当前学生数据全部为 `directions: ["TBD"]`，**When** 访客打开 Team 页，**Then** PhD 与 Master's 分组的每条记录都显示一个 `TBD` 标签，且不显示任何入学年份。
2. **Given** 某学生配置了多个方向标签，**When** 访客查看该行，**Then** 该学生的全部标签都可见，标签组位于姓名与成员链接之间。
3. **Given** 某学生没有配置成员链接，**When** 访客查看该行，**Then** 该行仍显示姓名与全部方向标签，且不渲染空的链接占位。

---

### User Story 2 - 内容维护者替换占位研究方向 (Priority: P1)

课题组维护者在 `students.json` 中把某位学生的 `TBD` 替换为真实研究方向（可多个），无需改动任何组件、样式或页面代码；重新构建后页面立即显示新的标签。

**Why this priority**: 占位符只是过渡状态，维护者必须能只改数据文件完成内容上线，符合站点「内容与展示分离」的既定原则。

**Independent Test**: 仅编辑学生数据文件，将一名学生的 `directions` 改为两个真实方向字符串，重新构建并查看 Team 页；确认两个标签按数据顺序显示，且其他学生、其他区块不受影响；随后恢复占位值。

**Acceptance Scenarios**:

1. **Given** 维护者把某学生的 `directions` 改为多个真实方向，**When** 构建并打开 Team 页，**Then** 该行按数据顺序显示全部标签，样式与其他学生一致。
2. **Given** 维护者漏写 `directions`、写成空数组或空字符串，**When** 执行构建，**Then** 构建失败并指明出问题的数据文件、学生姓名与字段。

---

### User Story 3 - 标签在支持视口内稳定排布 (Priority: P2)

访客在桌面、平板、手机的任意支持宽度下浏览 Team 页时，多个方向标签不会互相重叠、不会被裁剪或省略，也不会把页面撑出横向滚动；标签过长或过多时在行内自然换行，行高随之增高，姓名与成员链接仍保持清晰的左右对齐。

**Why this priority**: 研究方向标签数量与文本长度由内容决定，必须保证布局在任何视口下不破损，但可以在主展示替换完成后再验收。

**Independent Test**: 在 320 / 375 / 480 / 576 / 768 / 1024 / 1280 / 1440 / 1920px 视口下检查两个在读分组：标签文本完整可见、无元素重叠、无页面级横向滚动，双栏在 ≥768px 正常呈现。

**Acceptance Scenarios**:

1. **Given** 某学生有多个标签且视口较窄，**When** 访客查看该行，**Then** 标签组换行收纳，标签文本完整显示，姓名与链接不被覆盖。
2. **Given** 视口宽度 320px（支持的最窄宽度），**When** 打开 Team 页，**Then** 页面无横向滚动，标签、姓名与链接均完整可见。
3. **Given** 视口 ≥768px，**When** 打开 Team 页，**Then** 两个在读分组仍按 `ceil(n/2)` 切分为左右两栏，两栏顶线一致，栏距与既有规则相同。

---

### User Story 4 - 通过成员链接访问学生主页 (Priority: P1)

访客在 Team 页的在读学生名单中，可以看到每位学生至多一个成员链接标签（Homepage / GitHub / Scholar），点击后打开可核实属于该学生的页面；链接按「自建个人主页 → 机构个人资料页 → GitHub → Google Scholar」的优先级选取。没有可核实链接的学生不显示链接标签，页面不会把访客带到同名陌生人的页面。

**Why this priority**: 成员链接是访客了解学生研究工作的主要入口；错误链接会直接损害课题组的可信度，因此链接的归属正确性与展示本身同等重要。

**Independent Test**: 核对 `students.json`：每位学生的 `url` / `github` / `scholar` 至多一个非空；逐一打开链接，确认页面内容与本人身份一致；无链接的学生行不显示链接标签；构建通过。

**Acceptance Scenarios**:

1. **Given** 某学生有可核实的自建个人主页，**When** 访客查看该行，**Then** 显示 Homepage 链接并指向该主页，且不显示 GitHub / Scholar 链接。
2. **Given** 某学生只有可核实的 GitHub 或 Google Scholar 页面，**When** 访客查看该行，**Then** 显示对应的 GitHub 或 Scholar 链接。
3. **Given** 某学生没有任何可核实链接，**When** 访客查看该行，**Then** 该行不显示链接标签，姓名与方向标签正常显示。

---

### Edge Cases

- **`directions` 缺失 / 空数组 / 仅空白字符串**：构建失败，错误信息包含数据文件、学生姓名与字段名，不静默渲染无标签的行。
- **单个标签文本很长**（长于可用行宽）：标签文本不得被裁剪或以省略号截断；允许在标签内部换行收纳，且不得造成页面级横向溢出。
- **标签数量很多**：标签组在行内换行，行高增高；不得挤压或覆盖姓名、链接。
- **分组内某学生无链接**：不渲染链接，标签组与有链接的行遵循同一对齐规则，不出现空洞占位。
- **分组仅 1 条记录或为空**：沿用既有单栏（`.is-single`）与 "coming soon" 占位行为，本特性不改动。
- **数据文件条目顺序调整**：名单展示顺序随之改变，双栏切分仍按 `ceil(n/2)`，不重新排序。
- **历史归档文档**：`specs/001`–`012` 中出现的 `grade`/Since 记录保持原样，不作为待删除字段。
- **学生重名**：无法取得强关联证据时按「未找到」处理，链接留空，不凭同名猜测。
- **个人主页托管在 GitHub Pages**：按「自建个人主页」记入 `url`，不记为 `github`。
- **既有链接与更高优先级来源并存**：保留更高优先级来源并删除低优先级字段，避免三选一校验冲突。
- **链接失效或内容与本人不符**：视为无链接，不写入并在交付报告中列出。
- **`directions` 项含前后空格或重复项**：不视为构建错误；按原样渲染（不 trim、不去重），由维护者避免。
- **仅有 HTTP 版本的主页**：不符合 HTTPS 要求，视为无链接，三个字段保持 `null`；不写入 HTTP 链接。
- **两栏内行高不一致**：标签换行导致左右两栏同一序号的行高不同属于正常现象；只要求两栏顶线一致，不要求跨栏逐行对齐。
- **姓名达到 4 个汉字**：在 3.5em 姓名列内换行为已声明的预期行为（当前名单最多 3 个汉字），不按 Constitution VI.4 的非预期换行处理；本期不为此调整列宽。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 学生数据 MUST 以 `directions`（研究方向标签，非空字符串数组，至少 1 项）表达研究方向；学生记录 MUST NOT 再包含 `grade` 或任何表示入学年份的字段。
- **FR-002**: 当前全部在读学生的 `directions` MUST 为 `["TBD"]`；页面 MUST 原样显示 `TBD`，MUST NOT 以空字符串、空标签或省略标签的方式占位。
- **FR-003**: Team 页两个在读分组的每条记录 MUST 显示该学生 `directions` 的全部标签；MUST NOT 显示 "Since"、年级数字或任何入学年份。
- **FR-004**: 在读名单 MUST NOT 再按年级排序；每个分组内 MUST 保持数据文件条目顺序，既有按 level 分组与按 `ceil(n/2)` 切分两栏的规则保持不变。
- **FR-005**: 横向行（支持宽度 ≥480px）的视觉顺序 MUST 为「姓名 → 方向标签 → 成员链接」；标签 MUST 使用可辨识的标签样式，与姓名文本、链接文本在视觉上可区分，并沿用教师研究方向 chip 的既有视觉语言（浅色背景、4px 圆角、0.9rem、次级文字色；具体值以 `contracts/team-row.md §5` 为准）。
- **FR-006**: 每个标签的文本 MUST 完整可见，MUST NOT 被裁剪、遮挡或以省略号截断；标签组 MUST NOT 与姓名或成员链接发生元素重叠。
- **FR-007**: 标签组在可用宽度内 MUST 支持换行收纳；标签数量增加或文本变长时，行高可以增高，但 MUST NOT 造成页面级横向滚动。
- **FR-008**: 视口 <480px 时，每行 MUST 依次呈现姓名、方向标签组与成员链接；链接独占最后一行并右对齐，标签组不得覆盖或截断姓名与链接。
- **FR-009**: `directions` 缺失、不是数组、为空数组或包含空/空白字符串时，构建 MUST 失败，并指出数据文件、学生姓名与违规字段。
- **FR-010**: 数据维护文档 MUST 删除 `grade` 字段说明，并说明 `directions` 的格式、至少 1 项的要求、当前 `TBD` 占位约定、成员链接优先级（自建主页/机构页 → GitHub → Scholar）、HTTPS 要求与无链接时统一写 `null` 的约定。
- **FR-011**: 页面渲染、数据校验与数据文件中 MUST NOT 残留 `grade` 字段或基于 `grade` 的排序逻辑。
- **FR-012**: 当维护者填写真实研究方向时，标签内容 MUST 与课题组提供的权威信息一致，MUST NOT 凭推测填写（占位 `TBD` 为本次明确授权的临时内容）。
- **FR-013**: Faculty、Graduates、首页、发表页与新闻页对应的源文件与数据文件 MUST 保持零 diff（`git diff` 为准）；`graduates.json` 的 `year` 字段 MUST 保留。
- **FR-014**: 每个在读学生的方向标签 MUST 以 `role="list"` + `aria-label="Research directions"` 的标签组呈现，每个标签为 `role="listitem"`（供辅助技术识别为同一学生的研究方向集合）；标签顺序 MUST 与数据中的数组顺序一致。
- **FR-015**: 在读学生的成员链接 MUST 按「自建个人主页（含 GitHub Pages 学术主页）→ 机构个人资料页（如国科大/研究所个人页）→ GitHub → Google Scholar」的优先级择一填写；每位学生 MUST 至多一个链接字段非空；自建个人主页与机构个人资料页 MUST 写入 `url`，页面标签统一为 Homepage。
- **FR-016**: 写入链接前 MUST 至少取得一项强关联证据（页面或公开资料明确关联中科院信工所/国科大/G3（CIGMA）/在读层次/导师，或有与课题组成员合作的论文）；仅姓名相同的页面 MUST NOT 写入。
- **FR-017**: 学生没有任何可核实链接时，`url` / `github` / `scholar` MUST 统一写 `null`（schema 兼容省略），页面 MUST NOT 渲染空洞的链接标签；≥480px 的固定三轨布局天然保留链接列宽，无需额外占位元素，标签组可用宽度与有链接行一致。
- **FR-018**: 既有链接在找到更高优先级且可核实的来源时 MUST 被替换，替换时 MUST 删除低优先级字段；现有链接若被证实失效或不属于本人且无替代来源，MUST 移除并保持为空。
- **FR-019**: 本次补全 MUST NOT 改变成员链接的既有渲染与布局规则（Homepage / GitHub / Scholar 标签形态、右对齐、三选一校验均不变）。

### Key Entities *(include if feature involves data)*

- **在读学生（Student）**：姓名、培养层次（PhD / Master's）、研究方向标签列表（`directions`，至少 1 项）、至多一个成员链接（`url` / `github` / `scholar` 三选一，按自建个人主页 → 机构个人资料页 → GitHub → Scholar 的优先级选取；自建主页与机构资料页均写入 `url`）。
- **研究方向标签（Direction Tag）**：学生的一条研究方向文本；当前统一为占位值 `TBD`，后续由课题组提供真实内容替换。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Team 页两个在读分组共 31 条学生记录中，100% 显示至少 1 个方向标签；两个在读分组内显示 "Since" 或入学年份的位置为 0 处；全页 "Since" 为 0 处（Graduates 的 `year` 为毕业年份，不计入）。
- **SC-002**: 维护者仅修改学生数据文件即可把占位 `TBD` 替换为真实方向并在构建后正确显示，成功率为 100%，无需改动任何页面或样式文件。
- **SC-003**: 在 320 / 375 / 480 / 576 / 768 / 1024 / 1280 / 1440 / 1920px 九个视口下，两个在读分组的元素重叠、标签文本截断、内容溢出容器与页面横向滚动均为 0 处。
- **SC-004**: 对 `directions` 缺失、空数组、含空字符串的测试数据，构建失败率为 100%，且错误信息包含文件、学生姓名与字段。
- **SC-005**: Faculty、Graduates、首页、发表页与新闻页对应的源文件与数据文件相对实施前为 0 处 diff（以 `git diff` 为准）；Team 页在读学生分组与 4 个源文件为预期变更区。
- **SC-006**: 全部在读学生记录中，链接字段非空且超过 1 个的记录为 0 条；所有非空链接均按既定优先级选取并可公开核实，违规为 0 处。
- **SC-007**: 无任何可核实链接的学生 100% 以空链接渲染，且 100% 在交付报告中列出，供课题组人工补充。

## Assumptions

- **占位文案**：`TBD` 为已确认的占位文本，按数据原文渲染；将来替换为真实方向时沿用同一标签形态。
- **标签数量与长度**：不设硬性上限；页面通过换行收纳任意数量的标签。单个标签允许内部换行以避免截断。
- **名单顺序**：删除年级字段后，名单顺序等于数据文件条目顺序；当前数据文件按入学年份组织，视觉上仍大致保持原分组，但不再有排序保证。
- **数据形态一致**：`directions` 采用字符串数组，与教师数据的 `directions` 形态一致，便于维护者理解。
- **链接约束**：每人至多一个链接（`url` / `github` / `scholar`）的既有校验不变；本次补全按「自建个人主页 → 机构个人资料页 → GitHub → Google Scholar」择一。
- **链接核实**：以公开可检索页面为证据；同名但无机构、课题组、导师或合作论文等强关联线索的页面不写入，宁可留空。
- **视口范围**：支持的最窄视口为 320px；窄于 320px 不纳入支持与验收。验收以当前智能体工具的浏览器、100% 缩放与站点默认字体为准。
- **历史文档**：`specs/` 下既有特性的规格与验收记录是历史归档，其中提到的 `grade` / Since 不被视为需要清理的字段残留。
- **无链接写法**：数据文件统一写 `null`（schema 仍兼容省略）；页面不渲染占位。
- **维护建议**：不设硬上限；维护文档可给软建议（如每人 ≤5 个、单个标签 ≤30 字），实际以换行收纳为准。
- **31 条基线**：成功标准沿用 2026-11-22 的 31 条数据基线，不引入快照机制。
