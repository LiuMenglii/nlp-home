# Feature Specification: 项目内容结构重构（可维护内容与源码分离）

**Feature Branch**: `015-content-structure-reorg`

**Created**: 2026-11-24

**Status**: Draft

**Input**: User description: "请重构该项目。当前的项目结构不太便于后续维护：图片目录和图片说明分开，并且很多需要编辑的数据、新闻文件混在源代码中。请修改当前的项目结构，使项目更具有可维护性。"

## 目标与范围

当前仓库把维护者需要日常编辑的内容与源码混在一起，且图片与其说明分散在不同目录：

| 现状 | 问题 |
|------|------|
| `src/data/site.json`、`teachers.json`、`students.json`、`graduates.json`、`publications.json`、`gallery.json` | 结构化内容位于源码目录，与组件 / 页面 / 校验代码混杂 |
| `src/content/news/*.md` 与新闻配图 | 新闻正文与可在页面展示的图片位于源码目录 |
| `public/gallery/*.jpg` 与 `src/data/gallery.json` 中的说明 | 图片与 caption / 日期分处两个目录，新增照片需跨目录登记 |
| `public/teachers/*.svg` 与 `src/data/teachers.json` 中的成员信息 | 教师照片与姓名、职称、方向、简介等说明分处两个目录 |

本特性把所有「日常维护内容」集中到源码目录之外的单一顶层内容区 `content/`，并让每条带图片的记录（Gallery 照片、教师）以独立条目组织，图片与说明就近存放在同一位置。`src/` 只保留代码：组件、页面、样式、路由、构建与内容校验逻辑、Markdown 控件插件。

**范围之内**：

- 迁移站点品牌信息、教师、学生、毕业生、论文、Gallery 说明、新闻正文与新闻配图到顶层内容区。
- Gallery 与教师改为「每条记录一个独立条目」：每张照片 / 每位教师的图片与全部说明位于同一条目位置。
- 新闻保持「一文件一条」，正文与配图同目录；保留子目录与既有 URL 派生规则。
- 迁移后的内容区提供唯一、清晰的维护入口与字段说明（沿用并改写现有数据维护指南）。
- 同步更新构建期校验的定位路径与报错文案；更新文档中所有指向旧位置的指引。
- 图片最终访问路径允许变化；页面展示效果、内容、数量与排序必须与重构前一致。

**范围之外**：

- 不修改页面设计、布局、样式、交互、组件拆分、路由规则与 Markdown 控件行为；新闻页面 URL 保持不变。
- 不修改内容本身：成员、论文、新闻正文、图片内容与数量、文案与链接均保持原值。
- 不改动站点装饰性品牌资源（logo、favicon）的存放方式；它们不是带说明的日常内容，仍作为站点静态资源由品牌信息引用。
- 不重构学生、毕业生、论文三类数据集为逐条文件（它们不含图片，保持数组数据集以避免无谓拆分）。
- 不回溯改写 `specs/001`–`014` 的历史文档与 fixtures。
- 不新增依赖、框架或运行时能力；不改变 GitHub Pages 部署方式。

## Clarifications

### Session 2026-11-24

- Q: 可维护内容（新闻、成员、论文、照片等）应集中放在哪里？ → A: 统一顶层 `content/`，`src/` 只保留代码（用户确认）。
- Q: 图片与其说明希望以什么粒度就近组织？ → A: 每条记录一个条目——每张 Gallery 照片、每位教师各一个条目，图片与说明位于同一位置（用户确认）。
- Q: 图片的最终访问路径是否必须保持不变？ → A: 允许变化，只要页面展示效果、图片内容与数量不变（用户确认）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 维护者在一个内容区完成日常更新 (Priority: P1)

不熟悉前端代码的维护者接到任务：新增一篇新闻、更新一位教师、替换一张活动照片。他打开仓库根目录，能直接看到唯一的顶层内容区，在对应类型目录内完成全部编辑；全程不需要进入 `src/`，也不需要在源码里登记图片路径或说明。

**Why this priority**: 这是本次重构要解决的核心痛点——可编辑内容与源码混杂，导致维护者必须理解源码结构才能更新内容。

**Independent Test**: 在仓库副本中按内容区维护指南，只修改内容区文件完成「新增一篇测试新闻 + 新增一位测试教师 + 新增一张测试照片」，构建成功且三者在页面正确出现；删除测试条目后构建恢复原状，源码零改动。

**Acceptance Scenarios**:

1. **Given** 维护者只熟悉内容编辑、不熟悉前端代码，**When** 浏览仓库根目录，**Then** 能在唯一命名的顶层内容区找到全部可编辑内容；`src/` 下不存在新闻 Markdown、新闻配图、Gallery 照片、教师照片或成员 / 论文 / 站点数据文件。
2. **Given** 维护者新增一篇新闻，**When** 在内容区新闻目录新建 Markdown 并在同目录放入配图，**Then** 构建成功，新闻列表与详情按既有规则渲染，文章 URL 与既有派生规则一致。
3. **Given** 维护者新增一位教师，**When** 在内容区教师目录新建条目并在条目内放入照片，**Then** 构建成功，Team 页与首页教师名片均显示该教师的全部字段与照片，无需改动任何代码。
4. **Given** 维护者只想修改一位教师的照片，**When** 在该教师条目位置替换图片文件，**Then** 只有该教师名片变化，其他教师与图库不受影响。

---

### User Story 2 - 图片与说明就近，不再跨目录对照 (Priority: P1)

维护者查看一张 Gallery 照片或一位教师的照片时，caption、日期或成员信息与图片本身在同一位置，替换图片或修改说明都只涉及一处；不会再出现「图片在 public 下、说明在 src 数据文件里」的跨目录割裂。

**Why this priority**: 用户明确指出「图片目录和图片说明分开」是当前结构不可维护的主要原因之一；就近组织可直接消除图片与说明不同步的风险。

**Independent Test**: 逐一检查 12 张 Gallery 照片与 4 位教师：每张照片的 caption（及可选日期）与图片文件位于同一照片条目内，每位教师的姓名、职称、导师角色、研究方向、邮箱、链接、简介与照片位于同一教师条目内；任取一条修改后构建，仅该条目对应展示变化。

**Acceptance Scenarios**:

1. **Given** 12 张 Gallery 照片各有 caption 与部分日期，**When** 查看内容区，**Then** 每张照片的图片文件与其 caption / 日期处于同一照片条目位置，不需要跨目录对照。
2. **Given** 4 位教师各有照片与完整成员信息，**When** 查看内容区，**Then** 每位教师的图片与全部字段处于同一教师条目位置。
3. **Given** 新闻配有正文内图片，**When** 查看内容区新闻目录，**Then** 文章与配图同目录，相对路径引用规则保持不变。
4. **Given** 维护者替换某张 Gallery 图片，**When** 重新构建，**Then** 图库中该位置显示新图片且 caption / 顺序不变，其余照片不受影响。

---

### User Story 3 - 访客看到与重构前完全一致的站点 (Priority: P1)

访客访问首页、Team 页、发表页与新闻页时，看到的内容、数量、顺序、文案、链接与图片均与重构前一致；新闻文章 URL 不变，站内没有裂图。

**Why this priority**: 结构重构不得以任何可见内容或可用性变化为代价；这是重构可被接受的前提。

**Independent Test**: 分别在重构前后构建站点，逐页比对首页、Team、Publications、News 列表与 4 篇新闻详情：图库 12 张照片的顺序与说明一致；4 位教师、31 位在读学生、13 位毕业生、135 条论文、4 篇新闻全部存在且字段一致；所有图片正常加载；新闻 URL 完全一致。

**Acceptance Scenarios**:

1. **Given** 重构前首页展示 12 张 Gallery 照片，**When** 重构后访问首页，**Then** 12 张照片的数量、展示顺序、caption 与灯箱行为完全一致。
2. **Given** Team 页展示 4 位教师、31 位在读学生与 13 位毕业生，**When** 重构后访问 Team 页，**Then** 数量、分组、顺序、字段与链接完全一致，教师照片正常显示。
3. **Given** 重构前有 4 篇新闻详情页，**When** 重构后访问 `/news/<slug>/`，**Then** 4 个 URL 全部保持不变，正文、配图、BibTeX / 高亮 / 表格控件与摘要均与重构前一致。
4. **Given** 论文列表共 135 条，**When** 重构后访问 Publications 与首页代表性论文区，**Then** 条目、排序、CCF 徽标与链接完全一致。
5. **Given** 站点部署在 GitHub Pages 子路径下，**When** 重构后访问任意页面与图片，**Then** 所有资源均以正确的 base 前缀加载，无裂图、无 404。

---

### User Story 4 - 构建校验在新结构下继续拦截内容错误 (Priority: P2)

维护者漏放照片、照片路径写错、Gallery 超过 12 条、成员链接冲突或新闻摘要超限时，构建仍然失败，报错直接指出新内容区中出错的文件、条目与字段，避免错误内容静默上线。

**Why this priority**: 现有校验是内容正确性的安全网；重构必须保留其拦截能力，否则维护性提升会以错误上线风险为代价。

**Independent Test**: 对内容区构造一组违约输入（照片缺失、Gallery 第 13 条、成员双链接、非 HTTPS 链接、空研究方向、品牌字段为空、新闻摘要超 200 字符），逐项执行构建，确认每项均失败且报错指向内容区文件与字段；恢复后构建通过。

**Acceptance Scenarios**:

1. **Given** 某位教师的照片文件不存在，**When** 执行构建，**Then** 构建失败，报错指出该教师条目与照片字段，并提示图片应放入该条目位置。
2. **Given** Gallery 登记第 13 张照片，**When** 执行构建，**Then** 构建失败，报错指出内容区 Gallery 位置及超出数量。
3. **Given** 某成员同时填写两个链接字段，**When** 执行构建，**Then** 构建失败，报错指出成员姓名、冲突字段与所在内容文件。
4. **Given** 某新闻摘要超过 200 字符或含非法控件语法，**When** 执行构建，**Then** 构建失败，报错指出具体新闻文件与违规项。
5. **Given** 品牌信息缺少必填字段或 logo / favicon 指向不存在的资源，**When** 执行构建，**Then** 构建失败，报错指出内容区品牌信息文件与字段。

---

### Edge Cases

- **新闻子目录**：内容区新闻目录内的子目录 MUST 继续可用，详情页 URL 仍按相对路径派生（如 `lab-notes/probe` → `/news/lab-notes/probe/`）；既有单段 slug 的 URL 不得变化。
- **单篇新闻的专项校验**：现有针对 `self-taught-rlvr-2026` 的标题长度、标题原创性、摘要长度与控件语法校验，迁移后 MUST 继续作用于该文章的新位置。
- **图片引用为相对路径**：新闻正文中的相对图片引用在移动后 MUST 继续正确解析；构建可生成与旧地址不同的图片 URL，但页面必须正常显示。
- **旧位置残留**：迁移完成后旧位置 MUST NOT 保留内容文件副本；同一内容的唯一事实来源 MUST 只有一处，避免双向修改不一致。
- **空数据集**：学生 / 毕业生数组为空时，对应分组继续显示既有英文占位文案，构建不失败。
- **图片缺失 / 路径穿越**：照片字段指向不存在文件、包含 `/` 或 `..` 时，构建 MUST 失败并指出条目。
- **Gallery 顺序**：展示顺序 MUST 与重构前一致；排序规则 MUST 可被维护者理解和控制（如按照片日期或显式顺序字段），不得依赖文件系统返回顺序。
- **品牌资源**：logo / favicon 仍为站点静态资源；品牌信息文件中的路径校验（站内绝对路径、文件存在）MUST 保留。
- **历史文档**：`specs/001`–`014` 中出现的旧路径属于历史归档，不重写；新文档与报错信息不得再指向旧路径。
- **构建流水线**：GitHub Actions 的类型检查 + 构建步骤 MUST 无需功能性改动即可继续通过并部署。
- **并发维护**：同一照片条目内同时替换图片与修改说明，构建后二者一致生效；不会出现图片已换、说明未换的跨目录错配。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有日常维护内容 MUST 位于源码目录之外的单一顶层内容区 `content/`；重构完成后 `src/` MUST NOT 包含新闻 Markdown、新闻配图、Gallery 照片、教师照片，或成员 / 论文 / 毕业生 / 站点品牌数据文件。
- **FR-002**: 内容区 MUST 按内容类型提供清晰、可预期的组织：新闻、Gallery、教师、学生、毕业生、论文、站点品牌信息与维护指南各自有明确位置；维护者 MUST 能从根目录一眼定位到内容区。
- **FR-003**: 每张 Gallery 照片 MUST 是一个独立条目；该照片的图片文件与 caption、可选日期 MUST 位于同一条目位置；新增、替换或删除照片 MUST 只需在该条目位置操作，MUST NOT 需要跨目录登记。
- **FR-004**: 每位教师 MUST 是一个独立条目；姓名、职称、导师角色、研究方向、邮箱、UCAS 资料页、个人主页、简介与照片 MUST 全部位于同一条目位置；替换照片 MUST 不影响其他教师条目。
- **FR-005**: 新闻 MUST 保持「一文件一条」；正文与配图 MUST 同目录，相对引用规则保持不变；MUST 支持子目录且详情页 URL 派生规则不变。
- **FR-006**: 学生、毕业生、论文数据 MUST 迁移至内容区，并保持现有字段、数组结构与展示顺序；MUST NOT 因迁移而改变任何条目内容。
- **FR-007**: 站点品牌信息 MUST 迁移至内容区；其中 logo / favicon 仍为站点静态资源，品牌命名字段必填、资源路径必须在站点绝对路径下存在这两项校验 MUST 保留。
- **FR-008**: 重构后页面展示 MUST 与重构前一致：Gallery 12 张照片及其 caption / 顺序、4 位教师、31 位在读学生、13 位毕业生、135 条论文、4 篇新闻的数量、分组、顺序、文案、链接与图片均 MUST 不变；4 篇新闻的 URL MUST 不变。
- **FR-009**: 全部构建期内容校验 MUST 保留并在新结构下生效，包括但不限于：照片文件存在性与路径合法性、Gallery 上限 12 条、成员链接三选一、外链 HTTPS、研究方向非空、品牌字段完整、新闻摘要长度、特定新闻标题与摘要规则、新闻控件语法校验；任一违约 MUST 使构建失败。
- **FR-010**: 校验失败信息 MUST 指出内容区中的具体文件 / 条目、姓名或字段与修复方向；MUST NOT 继续引用旧路径。图片访问路径 MAY 变化，但任意页面 MUST NOT 出现裂图。
- **FR-011**: 内容区 MUST 提供唯一维护指南，说明每个内容位置放什么、字段含义、新增 / 替换 / 删除条目的步骤与构建验证方式；`docs/news-markdown-guide.md` 与根目录相关说明 MUST 同步更新为新结构，旧路径操作指引的出现次数 MUST 为 0（历史 specs 除外）。
- **FR-012**: 迁移 MUST 保证单一事实来源：旧位置的内容文件 MUST 删除，MUST NOT 保留重复副本；内容值（含图片内容）MUST 在迁移中保持不变。
- **FR-013**: 类型检查、构建与现有测试 MUST 通过；GitHub Actions 部署流水线 MUST 无需功能性修改即可完成构建与部署。
- **FR-014**: 除内容来源路径、校验报错文案与必要的加载配置外，组件、页面模板、样式、路由、Markdown 控件行为与站点 base / site 配置 MUST 保持不变。
- **FR-015**: 内容区的字段约定与注释 MUST 足以让不熟悉前端的维护者安全编辑，延续「内容与展示分离」的项目原则。

### Key Entities *(include if feature involves data)*

- **内容区（Content Area）**：源码之外的唯一顶层内容根，承载全部日常维护内容；不含构建逻辑与展示代码。
- **内容条目（Content Entry）**：带图片的一条内容记录（Gallery 照片、教师、新闻），由一个说明文件与其引用的图片组成；说明与图片位于同一位置。
- **内容数据集（Content Dataset）**：不含图片的结构化记录集合（学生、毕业生、论文、站点品牌信息），保持既有数组或对象结构。
- **站点品牌资源（Brand Asset）**：logo、favicon 等站点装饰性静态文件，由品牌信息引用，不属于日常内容条目。
- **内容校验（Content Validation）**：构建期对内容条目与数据集的字段、引用、数量与链接规则检查，失败即中断构建。
- **维护指南（Maintenance Guide）**：面向非前端维护者的唯一操作说明，覆盖内容位置、字段与更新流程。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 日常维护内容集中度 100%——7 类内容（品牌信息、教师、学生、毕业生、论文、Gallery、新闻）全部位于顶层内容区；`src/` 下可编辑内容文件数量为 0，旧位置内容文件数量为 0。
- **SC-002**: 页面一致性 100%——Gallery 12 张、教师 4 位、学生 31 位、毕业生 13 位、论文 135 条、新闻 4 篇的数量、顺序、文案与链接逐项比对一致；新闻 URL 变化数为 0；裂图数为 0。

## Assumptions

- **内容区位置与命名**：采用仓库根目录下的 `content/` 作为唯一内容区（用户确认）；`src/` 只保留代码。
- **条目粒度**：Gallery 与教师采用「每条记录一个条目」；学生、毕业生、论文与品牌信息不含图片，保留现有数据集形式，避免为拆分而拆分（遵循最小复杂度原则）。
- **图片路径**：允许构建后的图片访问路径变化（用户确认）；新闻文章 URL、页面路由与站内锚点不受影响。
- **品牌资源**：logo / favicon 属于站点装饰性资源而非带说明的内容，继续作为静态资源存放；品牌信息中的路径与存在性校验保留。
- **排序规则**：Gallery 与教师展示顺序以重构前为准；迁移后需要一条维护者可理解的排序依据，但具体字段由实施阶段确定。
- **内容零变更**：迁移只改变文件位置与组织形式，不改变任何文字、链接、字段值或图片内容。
- **历史归档**：`specs/001`–`014` 属于历史记录，不回溯修改其中出现的旧路径。
- **技术约束**：沿用当前静态站点框架与构建校验方式，不引入新依赖；GitHub Pages 部署方式与 base 路径不变。
