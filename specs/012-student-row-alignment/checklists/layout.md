## 需求变更记录（2026-11-22，已由 `/speckit-clarify` 同步到 spec）

**D1：三列固定宽度，两侧空白相等**

- 每行分三列：姓名列、Since 列、链接列。三列宽度在同一环境下固定，不随本行姓名长短或链接标签变化；同一分组的每一行使用同一套列宽。
- 姓名在列内左对齐，Since 在列内居中，链接在列内右对齐。
- 左侧空白 = 姓名列右缘到 Since 列左缘；右侧空白 = Since 列右缘到链接列左缘；两者相等，误差 ≤1px。
- 链接为空时，链接列仍保留原来的宽度（列定义还在，空着即可，不需要渲染占位元素）。因此空链接行与其他行的列位置一致，不会左右移动。
- 结果：同一分组内所有 Since 落在同一条竖线上；空链接不影响排版；Since 不要求在整行中点。
- 例：768px、三列分别 63 / 90 / 117px 时，三列共 270px，一行可用 296px，两侧空白各 13px。

**D2：列宽定为 3.5em / 5em / 6.5em**

- 姓名列 3.5em = 63px：当前最长是 3 个汉字（约 54px），留 9px；姓名换行不纳入本期（S2），以后出现 4 个汉字（约 72px）另行处理。
- Since 列 5em = 90px：Windows 当前约 85px，留 5px；Linux 回退约 90px，基本贴边。
- 链接列 6.5em = 117px：Windows 约 110px、Linux 回退约 114px，分别留 7px / 3px。
- 三列宽度固定，同一台电脑上不随内容变化；换字体只影响文字能不能放进列里，不影响列的位置。
- 不用 `max-content` 逐行算宽度：Homepage 行 110px、Scholar 行 80px，Since 会跳来跳去；如果以后要按内容自适应，必须整组共享同一套列宽（列表级网格或 subgrid）。

**D3：768px 的余量与风险**

- 三列合计 63 + 90 + 117 = 270px；768px 一行可用 296px；两侧空白各 13px，满足 ≥8px。
- 三列是固定宽度，768px 以上不会出现“三列总宽超过一行”；风险变成“文字比列宽”：姓名列有 9px 余量，链接列有 3–7px 余量，Since 列在 Linux 回退字体下几乎没有余量。
- 5em 是默认值。若实测某个环境的 Since 超过 90px，按 S1 改为 5.5em：63 + 99 + 117 = 279px，两侧空白仍有 8.5px，仍满足 ≥8px；不接受折行。

**选择 3.5 / 5 / 6.5 的代价**

- 在 768px 下，Since 中心固定在 63 + 13 + 45 = 121px，比行中点 148px 偏左 27px；26 条无链接行也会一起偏左，因为链接列始终保留 117px。
- 姓名列 3.5em 比当前最长姓名宽 9px；姓名左对齐，这 9px 会留在姓名列右侧。以当前 3 个汉字的姓名为例，列与列之间的空白相等（各 13px），“姓名文字到 Since 文字”的视觉空白约 24.5px，“Since 文字到链接文字”约 22.5px（Windows）/ 18.5px（Linux），比 4em 时均衡很多。
- 姓名换行不纳入本期（S2）；当前最长 3 字（约 54px）在 63px 姓名列内可容纳，以后出现更长姓名另行处理。
- Master's 分组没有链接，但固定第三列仍是 117px，所以和博士组对齐；空链接不需要额外占位元素。
- 5em 的 Since 列是本方案最紧的地方；链接列 3–7px 次之；姓名列 9px 最松。

## 重要问题（P1：会直接影响验收结论，或导致返工）

- [x] CHK001 - spec 有没有写明用哪个浏览器、哪种字体、什么缩放来验收？\[需求缺失, Spec §Assumptions, §SC-002]
  - **解释**：同一台电脑、同一个浏览器里字体是固定的；会变的是不同电脑之间。页面没有加载统一的字体文件，只是在 CSS 里排了一串候选（`global.css` 里的 `--font-sans`），浏览器会从本机已安装的字体里按顺序挑第一个。于是 Windows 通常用 Segoe UI，macOS 用系统字体，Linux 多半落到 DejaVu Sans 或 Noto Sans；中文还会再换一次中文字体。不同字体每个字的宽度不一样，Since 和链接占的地方就不同，向左让位的幅度也会变。spec 只说“按当前主验收字体度量，约 816px 及以上不再触发夹取”，但没写这个字体是什么，也没写浏览器和缩放比例。quickstart 里虽然提到 Segoe UI 和 Linux 回退字体，但那是验证指南，不在 spec 里。结果就是：两个人用不同电脑验收，可能一个说通过、一个说不通过，还都能引用 spec。
  - **建议**：在 Assumptions 里加一条验收环境：用最新版 Chrome 或 Edge，页面缩放 100%，字体用站点默认；主要结论以 Windows 默认字体 Segoe UI 的测量为准，Linux 回退字体的结果只记录、不判失败。再把“约 816px”改成“换字体后这个数值会变，实际以每行是否留出 8px 间距为准”。
- [x] CHK002 - SC-001 是否漏了 768px 这一档？\[覆盖不足, Spec §SC-001 vs §FR-002]
  - **解释**：FR-002 要求所有 480px 以上的横向行里 Since 都在中间。但 SC-001 列了 8 个宽度，唯独没有 768px。768px 是双栏最窄的一档：每行去掉左右留白只剩 296px，也是唯一会出现 Since 向左让位的地方。26 条没有链接的行在这一档能不能保持在 1px 误差内，现在没有验收标准。quickstart 的脚本其实已经测了 768px，只是 SC 没写。
  - **建议**：把 768px 加进 SC-001，变成 9 个宽度，写明“26 条无链接行在 768px 同样不超过 1px”。不需要额外工作，只是把最该测的一档写进标准。
- [x] CHK003 - 如果最窄情况下还是放不下，应该先保证什么？\[需求缺失, Spec §Edge Cases, §FR-004]
  - **解释**：现在只规定了“还移得动、能把 Since 和链接之间留出 8px”的情况。但如果左侧姓名至少留 72px，加上 Since、链接和两个 8px 间距，总宽度还是超过一行，spec 没说怎么办：让链接换行？让姓名区域再窄一点？允许挤进左右留白？还是直接算缺陷？research.md 里算过，Linux 回退字体下 768px 的 Homepage 行可能需要 297px，而一行只有 296px，这不是空想。没有规则，实现的人只能自己决定，验收的人也没法判断。
  - **建议**：在 Edge Cases 里补一条优先级：页面不横向滚动、元素不重叠最重要；其次是链接保持一行；最后才是姓名区域至少 72px。空间不够时，姓名区域可以变窄并逐字换行，链接不能换行、缩小或隐藏。如果这样还会挤进留白超过 1px，就按缺陷处理，停下来重新定方案。契约里“按缺陷上报”也引用这条。
- [x] CHK004 - SC-002 里的“最小左移”能不能直接量出来？\[不易测量, Spec §SC-002, §FR-004]
  - **注**：D1 生效后，“最小左移”不再需要；本条改为检查“两侧空白相等”能否直接量出来。
  - **解释**：先看一条 768px 双栏下的真实窄行：一行去掉左右留白后只有 296px。这一行里“Since 2022”占 85px，“Homepage ↗”占 110px，两个 8px 间距共 16px，剩下的 85px 就是姓名列：85（姓名列）+ 8 + 85（Since）+ 8 + 110（链接）= 296。
    - 如果三个要求都严格满足，姓名列和链接列应各分到 97.5px，Since 才会在正中间。但链接至少要 110px，比 97.5px 多 12.5px；链接不能缩，只能从姓名列里扣，姓名列就从 97.5px 变成 85px。
    - 姓名列少了 12.5px，Since 也跟着往左挪 12.5px。挪 12.5px 刚好让 Since 和链接之间留出 8px，挪更多没必要，所以叫“最小左移”。
    - 姓名列 85px 仍然高于 72px（4em）的下限，常见的 3–4 个汉字姓名（约 54–72px）放得下，所以这一行不会因为姓名被压而换行。
    - 这不是设计要求，而是窄屏下“Since 居中”和“链接贴右、还要留 8px”没法同时满足时的让步：先保证不重叠、留出 8px，Since 再尽量靠近中间，差额由姓名列吸收。
    - 麻烦在于：要知道“挪了 12.5px”，验收的人得先算出“如果没有链接、严格居中时会在哪”，这个位置在页面上看不见，很难操作。契约第 7 节已经换成三个能直接量的条件，但这些条件没有写进 spec。只看 spec 的人可能把正常的向左让位当成缺陷。
  - **建议**：把契约里的三个条件写进 SC-002：① Since 的中心不在行中点右边；② Since 右边缘到链接左边缘正好 8px（允许 ±1px）；③ 链接右边缘到行右边缘不超过 1px。三条都满足，就算“最小左移”，不用再倒推理论位置。

## 次重要问题（P2：影响可读性或边界一致性，通常补一句话即可）

- [x] CHK005 - spec 有没有写 Since 必须保持一行？\[需求缺失, Spec §FR-002, §Edge Cases]
  - **解释**：契约和 quickstart 都按“Since 只有一行”验收，但 spec 里没有这句话。如果窄屏下 Since 折成两行，居中的算法和行高都会变，验收的人却找不到依据。
  - **建议**：在 FR-002 或 Edge Cases 里加一句：“`Since <年份>` 必须保持一行，不能截断、省略或换行。”
- [x] CHK006 - 姓名太长换行时，Since 和链接跟第一行对齐，还是跟整块居中？\[表述不清, Spec §Edge Cases]
  - **解释**：spec 只说了长姓名要在左侧区域内换行、和 Since 保持 8px 距离；没说 Since 和链接应该跟姓名的第一行对齐，还是跟着变高的整行居中；也没说分隔线是否还横跨整行。契约里写了“按第一行对齐”，但只看 spec 的人不知道。
  - **建议**：在 Edge Cases 里加一句：“姓名换行时，Since 和链接保持一行，并与姓名的第一行对齐；行高随姓名变高，分隔线仍横跨整行；这种换行不算布局破损。”
- [x] CHK007 - “约 816px 以上不再向左让位”是必须做到的要求，还是只是观察？\[假设, 不易测量, Spec §Assumptions]
  - **解释**：这句话跟字体有关，却被写在 Assumptions 里，读起来像承诺；但验收的 11 个宽度里没有 816px，没法直接验证。它既不是必须达到的线，也不该成为争论点。
  - **建议**：标明它只是当前字体下的实测结果：“换字体后这个数值会变，实际以每行是否留出 8px 间距为准”。证据里可以顺便记一下 800px 和 820px，但不作为通过或不通过的依据。
- [x] CHK008 - 4 条链接都在左栏，右栏的链接情况需要单独验收吗？\[覆盖不足, 假设, Spec §SC-002]
  - **解释**：SC-002 只测 4 条有链接的行，而按现在的排序和切分，它们都在 PhD 左栏。右栏用的是同一套样式，出问题概率很低，但 spec 没说“右栏同理、不用单独测”，也没说要不要人为造一条右栏链接来检查。
  - **建议**：在 Assumptions 里加一句：“左右栏用的是同一套行内样式，结果一致，右栏有链接的行不单独设验收项。”如果想更保险，可以在 quickstart 里加一个可选检查：临时给右栏某行加一个链接看看，但不作为必须通过的项。
