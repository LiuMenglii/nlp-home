# NLP-HOME Constitution

## Core Principles

### I. 内容准确性（不可妥协）

- 站点展示的课题组信息（成员、论文、项目、新闻、招生等）MUST 与课题组提供的权威来源保持一致；
  发现过期或错误信息时视为缺陷，MUST 优先修复。
- 论文条目 MUST 与正式发表版本（DOI / 会议论文集 / 期刊页面）核对后方可上线；预印本与正式版
  信息冲突时，以正式版为准。
- 不确定或无法核实的信息 MUST 先向课题组负责人确认，不得凭推测填写。

### II. 内容与展示分离

- 课题组信息 MUST 以结构化数据文件（如 Markdown / YAML / JSON 数据源）形式维护，与页面模板解耦。
- 常规内容更新（新增论文、成员变动、新闻）MUST 只改动数据文件，MUST NOT 需要修改模板或样式代码。
- 数据文件 MUST 有清晰的字段约定与注释，使不熟悉前端的同学也能安全地维护内容。

### III. 静态站点与 GitHub Pages 交付

- 站点 MUST 为纯静态站点，通过 GitHub Pages 部署；MUST NOT 依赖服务器端运行时、数据库或付费服务。
- 发布分支的每次推送 MUST 能通过标准 GitHub Pages 构建流水线自动完成部署。
- 任何导致 GitHub Pages 构建失败的变更 MUST NOT 被合入。

### IV. 简洁学术化设计

- 页面视觉风格 MUST 保持简洁、学术化：以可读性和信息传达为第一优先级，MUST NOT 追求炫酷动效
  或过度装饰。
- MUST NOT 引入重量级前端框架或运行时依赖，除非有明确需求并在变更说明中陈述理由。
- 页面 MUST 在主流浏览器与移动端正常浏览。

### V. 最小复杂度（YAGNI）

- 站点结构 MUST 保持最简：优先选择长期维护成本最低的方案，不为假设的未来需求提前设计。
- 依赖数量 MUST 保持最少，新增依赖 MUST 说明必要性。
- 变更 MUST 保持小步提交，便于审查与回滚。

### VI. 无布局破损（不可妥协）

- 任何页面在支持的视口范围内 MUST 无布局破损。布局破损定义为以下任一情形：
  1. **元素重叠**：本应彼此分离的元素（文本、图片、标签、控件）在视觉上相互覆盖。
  2. **文字截断**：文本被裁剪或显示不全。有意的单行省略 MUST 在需求中明确声明省略规则与适用字段，
     未声明的一律视为破损。
  3. **内容溢出容器**：子元素的渲染区域超出父容器边界（含绝对定位越界、媒体撑破卡片）。
     容器内横向滑动作为已声明的交互手段时除外，但 MUST 不影响页面宽度。
  4. **非预期换行**：正常宽度下本应单行呈现的短语、标签或导航项发生换行，破坏对齐与可读性；
     正文段落等自然折行不属于破损。
  5. **页面横向溢出**：页面级出现横向滚动，即 `document.documentElement.scrollWidth` 大于
     `window.innerWidth`。
- 破损判定 MUST 基于真实浏览器渲染，覆盖项目声明的支持视口矩阵；MUST NOT 仅凭静态代码阅读或
  设计稿推断，MUST NOT 用 `overflow-x: hidden` 掩盖页面横向溢出。
- 布局破损 MUST 按缺陷处理，其修复优先级高于新增功能。
- 涉及模板、样式或响应式断点的变更 MUST 在合并前按上述口径逐项检查并记录结果。

## 内容与数据约束

- 技术栈：以静态站点方案为基础（具体生成框架在首个特性的 spec / plan 阶段确定），
  构建产物 MUST 完全兼容 GitHub Pages 托管。
- 成员信息仅收录学术展示所需内容（姓名、头像、研究方向、个人主页 / 邮箱链接等）；
  收录 MUST 经知情同意，知情同意的既定渠道为课题组提供收录名单——课题组向站点
  维护者提供名单，即视为名单内成员已完成知情同意，无需另行逐一征询个人同意；
  MUST NOT 包含敏感个人数据。
- 图片等静态资源 MUST 保存在仓库内并通过相对路径引用，MUST NOT 热链外部不稳定资源。
- 外部链接（DOI、个人主页、项目主页）MUST 指向权威来源并使用 HTTPS。

## 维护工作流

- 常规内容更新流程：修改数据文件 → 本地构建验证 → 提交并推送 → GitHub Pages 自动部署。
- 涉及模板、样式或构建配置的变更 MUST 通过 Pull Request 进行，合并前 MUST 确认本地构建通过、
  页面渲染正常且无布局破损。
- 每次内容变更部署后 MUST 检查线上页面的实际渲染效果（成员、论文列表等是否正确展示，
  以及在桌面与移动视口下是否存在布局破损）。
- 重大改版（更换框架、调整信息架构）MUST 先走 Spec Kit 流程（specify → plan → tasks）再实施。

## Governance

- 本 Constitution 是 NLP-HOME 项目的最高治理文档，与其他实践冲突时以本文档为准。
- 修订本 Constitution MUST：说明修订内容与理由、获得课题组维护负责人确认、按语义化版本规则
  递增版本号并更新 Last Amended 日期。
- 版本规则：MAJOR——原则删除或重新定义；MINOR——新增原则 / 章节或实质性扩充；
  PATCH——措辞澄清、笔误修正。
- 所有变更与审查 MUST 核对本文档的合规性；无法用简单方案解释的复杂度 MUST 在 PR 中给出书面理由。
